## Issue 1 (upstream OpenClaw): decisionModels manifest hard-caps questionTypes to 3, blocking the engine's full type set

**Title:** `decisionModels.questionTypes manifest cap (≤3: boolean/choice/score) blocks locally-supported decision types (text/number/date/box/boxes/noul)`

**Body:**

OpenClaw 2026.11.8 (2d4ab29).

A local decision plugin + runner (LiquidAI d1-Omni-2B-MLX-8bit via mlx-vlm) supports question types `noul, choice, score, text, number, date, box, boxes`. The gateway rejects any plugin manifest declaring more than 3 questionTypes, and rejects anything outside `boolean/choice/score` — enforced in `dist/manifest-capability-normalizers` (observed at install). Consequences:

1. Plugin lane can never expose text/number/date/box/boxes even when the engine supports them.
2. Gateway Decision V2 core itself only understands `boolean/choice/tags/score/sort` — so lifting the manifest cap alone is insufficient; contract widening must be coordinated across gateway core, tool schema, plugin codec, and validator.

Repro: declare `questionTypes: [boolean, choice, score, noul]` in a decisionModel manifest → plugin load rejects with cap error.

Requested: a roadmap for widening the decision question-type contract, or an explicit documented "3 types only" contract so plugin authors can rely on it. Currently the cap is undocumented and the dist is sha256-inventory-protected, so there is no supported local workaround.

Workaround in use: normalize richer types down to boolean/choice/score in an adapter (`d1-typesafe-adapter.py`: boolean→noul, criteria list→false/true maps, label→description maps) with reverse-mapping on answers. Works, but caps capability and adds a bridge service.

## Issue 2 (upstream OpenClaw): decision_evaluate arg validation collapses many distinct errors into one generic message

**Title:** `decision_evaluate: stacked validators emit one generic "provide state and a nonempty questions map" for at least 4 distinct arg defects`

**Body:**

OpenClaw 2026.11.8 (2d4ab29), tool `decision_evaluate` (contract v2).

Observed 2026-11-27 (9+ failed attempts logged in failure ledger; each defect produced an indistinguishable or misplaced error):

| Actual defect | Error returned |
|---|---|
| `state` omitted | "state: must have required property 'state'" (ok, precise) |
| `state` present but untagged (`{...}` instead of `{"type":"json","value":{...}}`) | "provide state and a nonempty questions map" — **misleading; state was present, tagging was the problem** |
| Extra top-level fields | generic map error, doesn't name the offending key |
| Malformed nested criteria shape | generic map error, doesn't name the question or field |

The untagged-state case is the worst: the message implies state is missing when it is present, sending callers in circles (this cost 3 retries in one session; source of the message appears to be dist/validation-v2 `validateDecisionBatchV2`, which validates the tag union after the presence check but reports the presence error).

Requested: per-defect error text naming (a) the failing layer (tool schema vs batch validator vs question validator), (b) the field path, (c) the expected shape. E.g. `state.type: untagged object; expected {"type":"json","value":…} or {"type":"text","text":…}`.

Also: the compact tool schema shown to models does not make `state` visibly required or show the tag union — worth surfacing in the tool description.

## Issue 3 (this repo): adapter 502s lose the engine's 400 detail

**Title:** `d1-typesafe-adapter.py returns HTTP 502 with lossy text on upstream 400; engine's structured validation errors are dropped`

**Body:**

`services/d1-typesafe-adapter.py` (:8009) proxies to the System One runner (:8090, `services/d1-systemone-server.py`). When the runner rejects a batch with 400 + a precise message (e.g. "score criteria must list 2-10 levels lowest first", "unknown question type 'text'", "instructions must be the question text"), the adapter returns 502 with generic text; the engine's detail never reaches the caller or the gateway log.

Impact: upstream issue 2's generic errors get *another* lossy layer; debugging requires tailing `logs/d1-server.err.log` by hand.

Fix: pass through the upstream 400 body verbatim as a structured error (`{"error": {"layer": "engine", "detail": <runner message>}}`), and only use 502 for genuine transport failures. Add a contract-test case asserting the 400 detail survives the round trip.

Evidence: 2026-11-27 test session — runner 400s for score-with-1-level and type=text; adapter surfaced 502 with no detail (ledger: "Engine 400s surfaced as adapter 502").
